# Explaining Edit and Delete

Scope:
- Applies to UpdateFlowBlock and UpdateManagedObject.
- Covers editing references, updating nested values, and safe deletion.

Type model:
- Reference Components: FlowBlocks, ManagedObjects (including FieldElements).
- FlowBloxReactiveObject-only (non-reference component): parent-scoped nested reactive values.

Update rules:
- Always use path-based updates: /Property/0/Nested.
- UpdateManagedObject accepts the fully qualified field name in name to target a FieldElement; other ManagedObjects use their Name.
- Never update ManagedObject-internal data through a parent path such as `UpdateFlowBlock /<ManagedObjectCollection>/0/...`; target it directly with `UpdateManagedObject`.
- Never guess/invent property names or nested paths; inspect target metadata first with `GetTypeKindsInfo` (or `GetManagedObjectKindsInfo` for managed objects) before write operations.
- For FlowBloxReactiveObject-only values:
  - never assign direct JSON object/array blobs to parent properties
  - set sub-properties by path
  - missing parent paths are created automatically (GetOrCreate behavior)
- Creation split:
  - FlowBloxReactiveObject-only: create/update via Update path
  - FlowBlocks: create via CreateFlowBlock, then reference via Update
  - FieldElements cannot be created with CreateManagedObject.
  - Multi-result FlowBlocks may pre-create output fields (e.g. WebRequest creates Content). `ResultFieldByEnumValue<TEnum>` pairs an EnumValue output key with a ResultField; the FlowBlock decides which keys are materialized. Inspect `GetComponentSnapshot`, reuse existing fields, and never create one field per enum value indiscriminately.
  - For a missing multi-result field, use CreateField with the owning BaseResultFlowBlock in sourceFlowBlockName (sets Source).
  - BaseSingleResultFlowBlock normally creates its default ResultField automatically. If you notice a missing ResultField in the available project context, repair it with CreateField using sourceFlowBlockName.
  - BaseSingleResultFlowBlock missing field creation: use DefaultResultFieldType for fieldType and, when set, DefaultResultFieldName for overrideName; otherwise use nameGenerationMode="DeriveFromFlowBlock" (the default for single-result blocks).
  - Create Input/Memory fields exclusively with CreateUserField. They have no source FlowBlock and receive `UserField=true`, `UserFieldType`, a default `TypeElement` (`FieldType=Text`), and the corresponding `Input_`/`Memory_` prefix.
  - Inspect FieldElement metadata with `GetManagedObjectKindsInfo`; update every FieldElement, including user fields, directly with UpdateManagedObject.
  - Other ManagedObjects: create via CreateManagedObject, then reference via Update.
- After CreateField, assign it to the appropriate result/reactive mapping with UpdateFlowBlock/UpdateManagedObject resolver syntax.

Known BaseFlowBlock collection semantics:
- `TestDefinitions`: ManagedObject reference collection; use Link/Unlink.
- `GenerationStrategies`: FlowBloxReactiveObject collection; use path-based nested updates, never Link/Unlink.

Typed index GetOrCreate (reactive-only collections):
- Optional syntax: /Collection/<index>:<FullTypeName>/...
- Needed mainly for abstract/polymorphic base types.
- If index already has different type: delete that index first, then recreate with requested type.

Link/Unlink (reference components only):
- Resolver formats:
  - {"resolveFlowBlockByName":"FlowBlockName"}
  - {"resolveManagedObjectByName":"ManagedObjectName"}
  - {"resolveFieldElementByFQName":"$FlowBlock::FieldName"}
- Single reference:
  - /Property/Link + resolver
  - /Property/Unlink (resolver optional)
- Collection reference:
  - /Collection/Link + resolver (no duplicates)
  - /Collection/Unlink + resolver (no-op if absent)
  - /Collection/<index>/Link + resolver (explicit replace/swap)
  - /Collection/<index>/Unlink (explicit index removal)
- Never use Unlink for FlowBloxReactiveObject-only values; use Delete on parent path instead.

Delete rules:
- Context delete via Update path:
  - /Path/Delete
  - /Collection/<index>/Delete
  - Applies only to FlowBloxReactiveObject-only (non-reference component) values in the current parent context.
  - Before reactive delete, the runtime checks IsDeletable; if blocked, remove blocking references first.
- Permanent delete for reference components:
  - DeleteFlowBlock / DeleteManagedObject
- Reference dependencies must be removed first (leaf-to-root), otherwise delete fails and returns blockedBy entries.
- blockedBy semantics: these are components that still hold references to the target object or its field elements.

Examples:
- Fb1 => Mo1 => Mo2: remove Fb1->Mo1 reference before deleting Mo1.
- Fb1 => Fb2 => Fb3: delete Fb3 first, then Fb2, then Fb1.
