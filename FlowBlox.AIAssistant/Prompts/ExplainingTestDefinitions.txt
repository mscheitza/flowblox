Use this only when the user explicitly asks to create/configure test cases.
If setup complexity is high or scope is unclear, load deep-dive catalog key `explaining_test_definitions_deep_dive`.

Goal:
- If the user provided test data for external or generated content, verify those values against an actual debug result before creating the test definition.
- Ensure the flow-block connections from the start block through the intended target are correct.
- Create only a `FlowBloxTestDefinition` managed object, preferably with just its name.
- Link it to the target flow block and let synchronization create all test data structures.
- Inspect generated test rows/entries.
- Apply focused updates only to the generated test configuration.

Generator-driven test setup:
- When the user requests a test-driven approach with generators, create/configure the test definition when the successively built flow first reaches a generator-dependent target, then follow `explaining_generators` and call `RunGenerationStrategies`.
- The Assistant must provide test evidence and expectations, not manually generate the selector/pattern/configuration that the generation strategy is meant to produce.

Hard rule -- never create test data manually:
- Never create, add, replace, or pre-populate `FlowBloxTestDefinition.Entries` / `FlowBlockTestDataset` objects.
- Never create, add, replace, or pre-populate `FlowBloxFieldTestConfiguration` objects.
- These objects are owned by automatic synchronization when the definition is linked to a target flow block. Only update the synchronized objects after reading them with `GetComponentSnapshot`.

Recommended tool-call order:
1. If the user supplies expected values/counts for dynamic content, run `RunProjectDebugTest` first. Use `GetLastDebugArtefact`, then `InspectFieldValue` with `searchValues` to verify that the values actually occur before creating the test definition. For links, also search likely relative and absolute URL variants.
2. Ensure all flow-block connections up to the target are correct; synchronization derives its scope from that connected flow.
3. `CreateManagedObject` with type `FlowBloxTestDefinition`, preferably setting only `Name`. Do not supply `Entries` or nested test configuration.
4. `UpdateFlowBlock` to connect the created test definition in `TestDefinitions` (exact property name).
   Use standard link operation, for example `path=/TestDefinitions/Link` with value `{"resolveManagedObjectByName":"<testDefinitionName>"}`.
5. `GetComponentSnapshot` with `kind=managedObject` and `name=<testDefinitionName>` to discover the automatically generated `Entries`, datasets, and field configurations.
6. Before any write updates, call kind info tools (prefer `GetTypeKindsInfo`, optionally `GetManagedObjectKindsInfo`) for `FlowBloxTestDefinition` and nested types to confirm paths/options.
7. `UpdateManagedObject` with precise path updates to existing synchronized objects to configure:
- per-entry execution behavior,
- field selection mode,
- user input / expected values,
- expectation conditions.
8. Optionally run `RunTestDefinition` when the user requests execution or when generator troubleshooting requires test protocol/test results.

Important behavior:
- Linking a test definition in a flow block's `TestDefinitions` auto-synchronizes rows from start to that target and sets that target row's `Execute=true`.
- Connecting/linking is the creation trigger for `FlowBlockTestDataset` and `FlowBloxFieldTestConfiguration`; a snapshot taken before linking is not a substitute for the required post-link snapshot.
- The link serves three purposes: assignment to the target/generator, convenient opening in flow-block context, and target/scope resolution. If opened from TestView without a current flow block, the latest linked/synchronized target in execution order is used.
- One test definition may be linked to multiple target flow blocks and can contain both branches after a shared predecessor. Do not create a separate definition merely because the flow branches.
- For each entry with `Execute=true`, activation prerequisites must be satisfied:
  - activation conditions of the flow block,
  - required fields must have a valid value strategy (at least manual input or an automatic selection mode),
  - for user-field configurations used by the test (`UserFieldType=Input`, and relevant `Memory` fields), use `SelectionMode=UserInput` and set `UserInput` explicitly. Do not rely on `Keep`: project defaults and locally loaded values can change, making the test non-reproducible,
  - for properties marked with `AssociatedFlowBlockResolvableAttribute`, resolve required associated flow blocks with `ResolveAssociatedFlowBlock` and ensure they are covered by the test setup.
- UI markers distinguish these prerequisites: the orange requirement marker denotes a required field value; the purple link marker denotes an associated flow block whose runtime state must be initialized, normally by setting its dataset `Execute=true`.
- `RequiredForExecution=true` means this test definition is executed automatically at runtime start. If an expectation fails, FlowBlox can run generation strategies on the affected flow block and repeat the step once.
- Do not set `FlowBloxTestDefinition.RequiredForExecution=true` by default. Only set it when the user explicitly wants runtime-start test guarding / automatic regeneration. Ask about auto-regeneration only if generation strategies exist on the affected flow block.
- `ExpectationConditions` are evaluated only for entries where `FlowBlockTestDataset.Execute=true`.

Examples:
1. WebRequestFlowBlock -> StartEndPatternSelectorFlowBlock
- In `FlowBloxTestDefinition.Entries`, set `Execute=true` for the `FlowBlockTestDataset` of `WebRequestFlowBlock` (must run first).
- In the selector entry, configure the relevant `FlowBloxFieldTestConfiguration` with `SelectionMode=First` (for the web request content field).
- Add `ExpectationConditions` for the selector output, typically:
  - one condition for expected extracted value,
  - one condition with `ExpectationConditionTarget=NumberOfDatasets` for expected result count.

2. WebRequest -> PatternSelector -> WebRequest -> PatternSelector
- Entry 1 (`WebRequestFlowBlock`): `Execute=true`.
- Entry 2 (first selector): read link candidates from entry 1, usually via `SelectionMode=First` on the relevant field configuration.
- Entry 3 (second `WebRequestFlowBlock`): use selected link from entry 2; for returned HTML/content field use the first value (again via `SelectionMode=First` where applicable).
- Entry 4 (second selector): define `ExpectationConditions` for extracted value and dataset count (`ExpectationConditionTarget=NumberOfDatasets`).

Invalid configuration (must avoid):
- Configuring expected outcomes (`FlowBloxFieldTestConfiguration.ExpectationConditions`) while parent `FlowBlockTestDataset.Execute=false` is logically invalid for that entry, because the flow block is not executed in the test run.
- `SelectionMode=UserInput` injects a value even when the producing flow block is not executed and therefore does not require a real result list. `SelectionMode=UserInput_ExpectedValue` is different: the flow block must execute and the supplied value must occur in its actual results.

Do not create test definitions proactively. Only do it when the user asks.

Test execution inspection:
- RunTestDefinition and RunGenerationStrategies retain full assignment/result values in the latest session/project artifact. GetLatestTestExecutionArtifact lists executions (including before/after generation); select executionId to retrieve limited rows and assignment keys.
- For truncated values, use InspectExecutedTestFieldValue with runId, executionId and fullyQualifiedFieldName; add datasetIndex for a result value and omit it for an assignment. Search with searchValues/searchIndex; LookAround adds surrounding context. Request the smallest useful maxTokens. No further debug run is needed.
