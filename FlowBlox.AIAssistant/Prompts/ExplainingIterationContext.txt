Explaining IterationContext and multi-input behavior:

1) Scope and timing
- IterationContext always references a flow block.
- The target flow block is executed once per iteration-end of the referenced flow block (once per dataset).
- Important: "iteration end" means the end of one iteration, not automatically the end of the full dataset stream.

2) Manual override and hard rule
- Manual override is possible via `AssociatedIterationContext` (Input -> IterationContext).
- Hard rule: do not set `AssociatedIterationContext` to a direct predecessor of the same target flow block.
- Hard rule: do not re-apply the same `AssociatedIterationContext` on direct successors if they are triggered only by that predecessor block.
- Reason: normal flow execution already guarantees that the successor is called by the predecessor. If the predecessor itself runs at `IterationContext` iteration-end, the whole downstream chain also runs in that same iteration-end dependency.

3) Multi-input combination and default resolution
- If multiple input flow blocks connect to one successor, FlowBlox combines input datasets based on each input flow block's `InputBehavior`.
- The default behavior is `First`: suitable when only one input dataset is expected or only the first input dataset is relevant.
- IterationContext default for multi-input: first common upstream flow block across all incoming paths.
- Successor executes once per resulting combined dataset.
- For each combined dataset, mapped values are applied before execution.

4) InputBehavior overview
- `Cross`: Cartesian combination of input datasets.
- `CrossValid`: Cross, only valid values.
- `RowWise`: combine row-by-row by index.
- `RowWiseValid`: row-wise, only valid values.
- `First` / `FirstValid` / `Last` / `LastValid`: select one dataset by position/validity.
- `InputBehaviorAssignments` are auto-synced with `ReferencedFlowBlocks`.

5) Collector flow-block special case (`BaseSingleResultCollectorFlowBlock`)
- Collects values across input datasets and emits one result when `CanGenerateResult()` becomes true.
- IterationContext resolution:
  - Highest priority: `AssociatedIterationContext`.
  - Otherwise: predecessor of the directly associated predecessor, or (if available) that predecessor's IterationContext.
  - If multiple predecessors are involved: first common upstream flow block.
- Typical decision:
  - `IterationContext = Reader` -> runs per reader row.
  - `IterationContext = Start` (or wrapping predecessor) -> runs once after full reader run.

6) Related topic
- For normal execution order, dataset propagation, and nested successor behavior in standard flow execution, see `ExplainingFlowLogic`, section: `Execution Order of Next Flow-Blocks (Sibling case)`.

7) Best-practice pattern: sibling extractors -> one output row per capture
- Pattern:
  - one capture/scope block (for example `WebSelector`, `WebEvent`, or `WebRequest` result scope)
  - sibling extractors for fields A/B/C
  - one multi-input consumer (for example `TableWriter`) connected to all extractor outputs
- Expected default behavior:
  - IterationContext resolves to the first common upstream capture block.
  - Consumer executes once per capture iteration and writes one combined row per capture dataset.
- Why default `First` usually fits here:
  - if each extractor returns exactly one value per capture iteration, selecting the first input dataset keeps the combination 1:1.
- Why `Cross` would also work:
  - if each extractor returns exactly one value per capture iteration, the Cartesian combination also produces exactly one combined dataset.
- Data quality guard:
  - if columns are mandatory, enforce requirements (for example required column mapping and/or required input fields) to avoid writing partial/empty rows.
