Use this guidance for controlled loops whose target lies earlier on the incoming execution path.

Choose the block by intent:
- `RecursiveCallFlowBlock` executes `TargetFlowBlock` itself again. It does not transfer fields. Use it when an operation must genuinely run again with its current inputs, for example polling a table or retrying a request.
- `InjectionFlowBlock` transfers values through `FieldTransferConfigs` into the output fields of `TargetFlowBlock`, then executes the target's successors. The target itself is not executed again. Use it to hand new state into an already completed result step, for example a next-page URL.

Mental model:
- Recursive call: "run that earlier operation again".
- Injection: "treat these mapped values as the earlier result and continue after it".

Required setup:
1. Connect exactly one incoming execution path to the recursive/injection block.
2. Set `TargetFlowBlock` to a block on that upstream path. The block itself and unrelated branches are not valid targets.
3. For Injection, configure `FieldTransferConfigs` with `TransferFrom` and `TransferTo`. Every output field of a result target must be covered.
4. Ensure only the repeat path reaches the recursive/injection block; the success or termination path must bypass it.

Retry/polling example:
- Flow: `TableReader -> result check -> no-result branch -> DelayFlowBlock -> RecursiveCallFlowBlock`.
- Set the `RecursiveCallFlowBlock` target to `TableReader`.
- Configure the no-result branch with conditions so Delay and Recursive call run only while no row/result is available.
- `DelayFlowBlock` prevents a tight loop; the recursive call then executes `TableReader` again.
- When rows are returned, route execution through the success branch instead, so the recursive call is no longer reached.
- For bounded retries, execute an `IndexFlowBlock` in the retry branch and require its result to satisfy `Index < RetryLimit` before continuing to Delay and Recursive call. Set the Index block's `AssociatedContextualObject` to the flow block immediately before the recursive target (for example the predecessor of `TableReader`), so the counter resets for each new outer input context while recursive attempts within that context keep incrementing. Once the limit is reached, the condition is false and no further recursive iteration is created.

Paging/injection example:
- Typical chain: `page entry -> item extraction -> next-page discovery -> InjectionFlowBlock`.
- Set the page-entry result block as the Injection target and map the discovered next-page URL/state to its corresponding output field.
- Injection resumes at the page-entry block's successors using the new state, without repeating the page-entry block itself.
- Keep next-page discovery on the per-page path, not below a per-item iterator; otherwise it runs once per extracted item.
- The loop stops when no usable next-page value reaches the Injection path.

Important behavior:
- Connections originating from either block set `TargetFlowBlock`; they do not create a normal `ReferencedFlowBlocks` edge.
- The target must already be reachable through `ReferencedFlowBlocks`; this prevents jumps into unrelated branches.
- Prefer stable, semantically equivalent source/target fields for Injection mappings.
- Every recursive path needs a reliable termination condition. For bounded retries, guard Delay and Recursive call with `Index < RetryLimit` using an appropriately contextualized `IndexFlowBlock`; when the condition becomes false, no further recursive iteration is created.
- Recursion inside an iteration context waits for all results, including recursive results, before an associated collector continues.
