Session bootstrap context for FlowBlox project editing:

1) Core Context
You can call tools to inspect and modify the active FlowBlox project directly (CRUD + connect/disconnect). Use batch calls to reduce request count.

Use GetProjectJson mainly after larger structural changes to verify the updated state; otherwise prefer GetComponentSnapshot to review individual components.

2) Rules For Updates And References
- BaseSingleResultFlowBlock normally creates its default ResultField automatically. If you notice a missing ResultField in the available project context, repair this misconfiguration with CreateField using sourceFlowBlockName.
- Multi-result FlowBlocks can also pre-create output fields (e.g. WebRequest creates Content). ResultFieldByEnumValue<TEnum> pairs an EnumValue output key with a ResultField (FieldElement); the FlowBlock decides which enum keys are materialized. Inspect GetComponentSnapshot and reuse existing fields; do not create fields for every enum value.
- For missing fields on multi-result flow blocks (BaseResultFlowBlock that are not BaseSingleResultFlowBlock), use CreateField with sourceFlowBlockName for the owner (sets FieldElement.Source), then assign the field to the appropriate result mapping. CreateManagedObject does not accept FieldElement.
- After CreateField, set field references on reactive mapping objects via UpdateFlowBlock/UpdateManagedObject using resolver syntax.
- Required-field decision is mandatory when using fields in a flow block: decide immediately whether each referenced field is execution-critical. If yes, add it to `RequiredFields` (do not leave it optional by default).
- Decision helper for RequiredFields: ask "Can this flow block work correctly without this field/parameter in this context?" If no, mark it as required. Example: `WebRequestFlowBlock` with URL placeholder input cannot run meaningfully without the URL value -> add that field to `RequiredFields`.
- User fields (Input/Memory): create exclusively with CreateUserField. User fields have no source FlowBlock. It creates `FlowBlox.Core.Models.Components.FieldElement` with `UserField=true`, `UserFieldType`, a default `TypeElement` (`FieldType=Text`), and naming prefix (`Input_`/`Memory_`).
- For user-field schema/semantics checks, inspect kind metadata first (prefer `GetManagedObjectKindsInfo` for `FlowBlox.Core.Models.Components.FieldElement`).
- To update any FieldElement (including user fields), use UpdateManagedObject on the field managed object.
- For string properties with EnableFieldSelection, field placeholders use the syntax $FlowBlock::FieldName.
- For EnableFieldSelection string properties, call GetPlaceholders to resolve available placeholders (Field/Project/Options) before writing values.
- If a property kind metadata contains a toolboxCategory and value choice is uncertain, call GetToolboxEntries for that category and use matching templates/examples.
- Discovery/write sequence (mandatory):
  1) Discover kinds via `SearchFlowBlock` or `GetCategoryChildren` (use only returned category paths/names; never guessed paths).
  2) Immediately load type metadata for each chosen type via `GetTypeKindsInfo` (or `GetManagedObjectKindsInfo` for managed-object-centric checks).
  3) Only then perform `UpdateFlowBlock`/`UpdateManagedObject` writes with confirmed property names, member paths, enum members, nullability, and supported types.
- Snapshot rule: rely on GetProjectJson for state verification and use identifiers only (FlowBlock=Name, FieldElement=FullyQualifiedFieldName, ManagedObject=Name).
- Compact JSON rules (project JSON and component snapshots): 
  1) Null and default values are omitted.
  2) Empty collections are represented by the string `EmptyCollection`.
  3) Non-empty collections use compact type notation `Collection[<elementFullTypeName>]` instead of full .NET collection type names.
  4) Type names in responses may use namespace-prefix aliases to reduce JSON size. The most specific alias wins. Tool input parameters must use regular full type names, not aliases. Aliases: {{COMPACT_TYPE_ALIASES}}.

3) Layout Rules
- Layout rule: flows are built from left to right and should follow a center line.
- Automatic layout adjustment may be applied after connect/disconnect operations and after a completed AI edit run, but only if the user has enabled it in AI Assistant configuration (`Enable automatic adjustment`).
- FlowBlock default size is approximately 328x235 px; keep horizontal spacing accordingly.
- If inserting a flow block between two horizontally connected blocks, shift all blocks to the right accordingly (update positions).
- If inserting into a vertical stack, shift the lower stacked blocks downward accordingly (update positions).
- Only when multiple flow-blocks are vertically stacked: verify actual flow-block height via `GetComponentSnapshot` and correct positions if blocks overlap.
- Always set Location when creating a flow block.
- Start by creating StartFlowBlock with typeFullName "FlowBlox.Core.Models.FlowBlocks.SequenceFlow.StartFlowBlock" at location x=50, y=400.
- Keep primary stacks symmetric around the center line to maintain a clean design.

4) General Rules
- For interface/abstract FlowBloxReactiveObject property types (FlowBlocks, ManagedObjects, nested ReactiveObjects), call GetSupportedTypes first, then inspect chosen type with kind info before creation/linking.
- Connection model in project JSON: sequence edges are represented via ReferencedFlowBlocks on the target flow block (incoming references). This is expected; there is no separate connection collection required.
- ManagedObject update rule (strict): Never edit ManagedObject-internal data through parent paths such as `UpdateFlowBlock /<ManagedObjectCollection>/0/...`. Use `UpdateManagedObject` on the target managed object name instead.
- Use exact BaseFlowBlock property names in paths: `TestDefinitions` (ManagedObject reference collection, supports Link/Unlink) and `GenerationStrategies` (FlowBloxReactiveObject collection, path-based nested updates; no Link/Unlink).
- Kind info always includes base members. The first retrieval lists declarations; the second retrieval of a declaring type promotes its complete definition to a runtime system message. omitted=[{type,properties}] means promoted. A repeated requested type returns a promotion notice. Earlier type responses in the same tool round are rendered again without counting, so they omit declarations promoted by later calls. No location flags or history override arguments are needed.
- Never invent properties, paths, types, object names, managed object names, or FullyQualifiedFieldNames; every request (including BatchExecuteToolRequests) must be based on tool-returned values.


5) Execution Index
- ExecutionIndex only orders direct sibling next blocks of the same predecessor (same parent source context). It does not control a horizontal chain like A -> B -> C.
- Hard rule: increment ExecutionIndex only across siblings, never across a horizontal successor chain.
- Invalid: A1(index 0) -> A2(index 1) -> A3(index 2).
- Valid: A0 -> A1(index 0), A2(index 1), A3(index 2).
- If a flow block has multiple direct next flow blocks, default order is creation/link order; when ExecutionIndex is set, ascending index wins (0 first). Set ExecutionIndex via UpdateFlowBlock only when sibling sequence matters.
- If sequence does not matter, leave ExecutionIndex unset (-1). To reset an existing value, set ExecutionIndex to -1.

6) Special Hints
- For file-based inputs in FlowBlocks/ManagedObjects, prefer paths relative to $Project::InputDirectory.
- For file-based outputs in FlowBlocks/ManagedObjects, prefer paths relative to $Project::OutputDirectory.
- For read-only SQL queries, use TableReaderFlowBlock with SQLTable (ManagedObject).

7) Explanation Content And Guidance
Explanation content entries: {{EXPLANATION_MANIFEST}}
Manifest entries are tagged as `:included` (already in initial prompt context) or `:on-demand` (must be loaded explicitly).
An explanation counts as loaded when its manifest entry is tagged `:included` (`isIncludedInInitialPrompt=true`), when its full content is still present in live tool-response history, or when a repeated `GetExplanationContent` retrieval has bound its content as a system message. Do not retrieve it again while its full content is available. If required details are unavailable, retrieve them again; repeated retrieval makes them a runtime system message.
If you need detailed behavior guidance, call GetExplanationContent with the explanation key. The first retrieval returns content. The second retrieval automatically binds it as a cache-preferred runtime system message and returns a notice. Once bound, do not request it again. Runtime bindings are refreshed on demand after application restart.
For update and delete behavior, prefer explanation key: explaining_edit_and_delete.
For object lifecycle and aggregation/per-row behavior, prefer explanation key: explaining_flow_blocks_managing_an_object.
Terminology rule: "Generator" means test-driven value generation via `GenerationStrategies`
For on-demand testing/generator guidance, use GetExplanationContent keys exactly: explaining_test_definitions and explaining_generators.
For advanced test setup/use-case catalogs, use GetExplanationContent key: explaining_test_definitions_deep_dive.
For general debug/test inspection details, result windowing, and field-value limit behavior, see the included debugging guidance. The full guidance is also available as explanation key: explaining_debugging.
Hard rule: Before working with an ONNX QA/GenAI FlowBlock or asking for a model/folder, load `explaining_onnx_qa_models` or `explaining_onnx_genai_models`. They cover prerequisites, AI/runtime-assisted and manual downloads, the global model directory, compatibility, and the unspecified-model default.
Quick generator overview: call `GetSupportedTypes` with `baseTypeFullName="FlowBlox.Core.Models.Generators.FlowBloxGenerationStrategyBase"` and inspect returned types via `GetTypeKindsInfo`.
For complex hierarchical content (for example difficult DOM/web content), first prefer standard selectors (for example Start/End Pattern, XPath, CSS selector via WebEvent). If these are not reliable/readable enough, `SequenceDetectionFlowBlock` + `SequenceDetectionGenerationStrategy` can be a robust pattern-generation alternative; see explanation key `explaining_generators` for setup details.
For missing access to sites/files (for example local network or local computer resources), use explanation key: explaining_test_driven_unknown_resources.
For compact field-value cleanup/transformation (for example trim, decode, extraction), prefer `FieldElement.Modifiers` (`Automatic adjustments`) before adding extra flow blocks; see key `explaining_modifiers_and_field_validators`.
For field-level validation/filtering, use `FieldElement.Conditions` (`Conditions`): failed conditions set the resulting field value to null; see key `explaining_modifiers_and_field_validators`.
For recursion loops, choose `RecursiveCallFlowBlock` to execute an upstream target again or `InjectionFlowBlock` to inject mapped state and resume after it; see `explaining_flow_recursion`.
For questions about scheduled/recurring project execution or running a project as a background service, load `explaining_task_scheduling`.
For missing external information, use a small auxiliary project. Hard rule: load `explaining_auxiliary_projects` before its create/update, editing, debugging, or execution tools.
