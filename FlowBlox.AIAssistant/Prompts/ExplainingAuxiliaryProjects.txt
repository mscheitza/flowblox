Auxiliary projects

Use only for small helper flows that obtain information missing from the user request or main project, such as an SQL schema, web content, or search result.

Distributed templates:
- Before creating an auxiliary project, call `GetAuxiliaryProjects(mode="distributedData",filter=...)`. It searches project names and descriptions and returns `fileName`, `description`, `inputFields`, and `outputFields`; omit `filter` to list all templates.
- Reuse a suitable file directly with `CreateOrUpdateAuxiliaryProject(mode="full_content",copyFromDistributedData={dataType:"auxiliary_project",fileName:<catalog fileName>},...)`. Use `GetDistributedDataContent(dataType="auxiliary_project",fileName=...)` only when its project JSON must be inspected or adapted first.
- Available templates may include flows for retrieving a page DOM from a URL, web searches, or database schema information such as table names and core column specifications. The catalog can grow over time.

Default workflow:
1. Search distributed templates with `GetAuxiliaryProjects(mode="distributedData",filter=...)` and prefer a suitable one.
2. Call `GetAuxiliaryProjects` (default `mode="session"`) for this session's existing projects, descriptions, inputs, outputs, file paths, and open state. Reuse one when suitable; otherwise copy a template or create a minimal project with `CreateOrUpdateAuxiliaryProject`.
3. If changes are needed, call `AuxiliaryProjectEditing(EDIT)` and use the normal project tools.
4. While it is active, validate the smallest relevant path with `RunProjectDebugTest(reason,inputParameters)`. Read protocol output directly, generated results/field changes with `GetLastDebugArtefact`, and truncated debug values with `InspectFieldValue`. Fix and repeat only as needed.
5. Hard completion rule: after `EDIT` and all required editing/debugging steps, always finish with `AuxiliaryProjectEditing(SAVE)` (closes by default).
   - Verify `isOpen=false` with `GetAuxiliaryProjects` before reporting completion or using the project through `ExecuteProject`.
   - Keep it open only while work or a user decision is pending; never leave an edited project unresolved when the requested work is complete.
   - Use `CLOSE` only to discard unsaved changes.
6. For regular use, call `ExecuteProject(projectFile,reason,inputParameters,outputFields)` with the path from `GetAuxiliaryProjects`. It returns declared project outputs without another token-intensive debug run. Use `InspectOutputFieldValue` only for truncated outputs.

Create/update contract:
- `metadata_only`: create an empty project or update its description; `description` is required.
- `full_content`: provide exactly one source, either `projectJson` or `copyFromDistributedData`; optional `description` overrides source metadata.
- To rename, use `metadata_only`, pass the old name as `existingProjectName` and the new `projectName`. The filename follows the new name; an existing target filename is rejected.
- File-level updates are rejected while an auxiliary project is open.

Storage and safety:
- Projects are isolated below `$Options::Paths.LocalAppDataDir\ai_assistant_auxiliary_projects\<session-hash>` and remain active across assistant runs until `SAVE` or `CLOSE`.
- For debugging or executing an auxiliary project, provide `reason` and call the tool directly. FlowBlox requests confirmation in the UI automatically; do not ask the user separately.
- Pass secrets or main-project values through execution `inputParameters` using placeholders; keep flows read-only where possible and outputs bounded.
- Main-project extensions are not transferred.
